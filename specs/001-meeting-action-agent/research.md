## R-01. STT 모델·실행 방식

**요구**: 한국어, 최대 2시간, 발언 시작 시각(초 단위), 신뢰도 지표 (SPEC US-01, 12장). 테스트는 가상 회의만 사용한다.

| 후보 | 장점 | 우려 | 검증 필요 |
|---|---|---|---|
| OpenAI Whisper (`openai-whisper`) | 한국어 지원, 세그먼트별 `avg_logprob`·`no_speech_prob`·`compression_ratio` 제공 | 2시간 입력의 처리 시간, GPU 의존 | 사용 가능한 모델 크기별 한국어 품질 |
| faster-whisper (CTranslate2) | 같은 계열 모델을 더 빠르게 실행, CPU에서도 현실적 | 지표가 원본과 완전히 같은지 | 지표 제공 범위, 설치 환경(Windows) |
| WhisperX | 단어 단위 정렬 + diarization 연동이 한 묶음 | 의존성이 무겁고 Windows 설치가 까다로울 수 있음 | 한국어 정렬 모델 지원 여부 |
| 클라우드 STT API | 설치 부담 없음, 화자 구분 내장인 경우가 많음 | 회의 음성의 외부 전송, 비용 | 실제 회의 적용 시 보안 정책 |

**평가 기준**: ① 한국어 단어·문장 정확도(CER/WER) ② 타임스탬프 오차 ③ 신뢰도 지표 제공 ④ 2시간 처리 시간 ⑤ Windows 설치 난이도 ⑥ 음성 외부 전송 여부 ⑦ 라이선스.

**알려진 위험**: Whisper 계열은 무음·잡음 구간에서 없는 문장을 생성한다고 보고된다 (**검증 필요**). 이는 "녹취에 없는 사실 생성 금지"와 직결되므로 VAD(무음 구간 제거) 적용 여부와 `no_speech_prob` 활용을 함께 검토한다. 잘못된 녹취가 들어오면 Reviewer 코드 검증기는 그 녹취를 정답으로 보고 통과시키므로, STT 오류는 Reviewer가 막지 못한다.

**잠정 결론**: 로컬 실행 Whisper 계열(faster-whisper 우선)로 시작하고, R-10의 음성으로 후보 2~3개를 비교한다. 클라우드 API는 보안 정책 확인 전에는 쓰지 않는다. 테스트 데이터는 가상이므로 개발 단계에서는 제약이 없다.

## R-02. 화자 구분 방식

**요구**: 발언마다 화자 라벨, `speaker_map`으로 실명 매핑 (SPEC 5.1). 화자 구분은 Whisper와 별도로 처리한다 (CLAUDE.md).

| 후보 | 비고 | 검증 필요 |
|---|---|---|
| pyannote.audio | 널리 쓰이는 오픈소스 diarization. 모델이 접근 승인과 토큰을 요구하는 형태로 알려짐 | 모델 라이선스·접근 조건, 한국어 회의에서의 품질 |
| WhisperX 통합 | STT와 diarization 정렬을 한 번에 | R-01과 함께 평가 |
| 클라우드 STT 내장 | 구현이 단순 | R-01의 보안 문제 |
| 수동 매핑만 | 자동 구분 없이 사람이 라벨 지정 | MVP 시연성이 낮음 |

**설계 쟁점**
- diarization이 내는 `SPEAKER_00` 같은 라벨을 `speaker_map`으로 실명에 매핑한다. 매핑이 없으면 라벨을 그대로 쓰고 지시자는 `확인 필요`다 (SPEC 5.1). 화자 구분이 틀리면 **자기 할당("제가 하겠습니다")의 담당자**가 틀어진다. 이 경우 `speaker_map` 오류가 곧 허위 담당자가 되므로, 자기 할당 담당자는 매핑이 사람 확인을 거친 경우에만 실명으로 쓰는 방안을 검토한다.
- 발언 경계를 STT 세그먼트로 할지 화자 전환 구간으로 할지 정해야 한다. 한 STT 세그먼트에 두 화자가 섞이면 `speaker`와 `timestamp`가 어긋난다.
- 동시 발화 처리 기준.

**잠정 결론**: pyannote 계열(또는 WhisperX 통합)을 첫 후보로 하고, R-10으로 평가한다. 정확도가 부족하면 `speaker_map` 수동 보정 단계를 UI에 둔다. 화자 구분은 P7(후순위)이므로 P1~P6은 가짜 녹취 JSON으로 진행해 이 결정에 막히지 않는다.

## R-03. `low_confidence` 판정 기준

**요구**: STT 신뢰도가 낮은 발언에 표시하고, 그 발언만 근거인 판정은 `확인 필요`로 둔다 (SPEC US-01, 5.6).

- 후보 신호: 세그먼트의 `avg_logprob`, `no_speech_prob`, `compression_ratio`(openai-whisper가 내는 값), 단어 단위 확률(정렬을 쓰는 경우).
- openai-whisper는 디코딩 실패 판단에 기본 임계값(logprob -1.0, no_speech 0.6, compression ratio 2.4)을 쓴다 (**검증 필요**). 이를 `low_confidence`의 **출발점**으로 쓰되, R-10 음성에서 오인식 구간과 대조해 튜닝한다.
- 어떤 지표를 쓰든 판정 기준과 값을 설정 파일로 분리해 튜닝 가능하게 한다.

**잠정 결론**: 위 세 지표 중 하나라도 임계값을 넘으면 `low_confidence: true`. 정확한 값은 벤치마크 후 SPEC에 기록한다.

## R-04. 이행 매칭 확신도

**요구**: 신규 회의 발언을 이전 Action과 매칭하고 확신도(상/중/하)를 정한다. 하이면 `확인 필요` (SPEC 5.6).

- 단계: ① 후보 발언 추리기(키워드, 담당자명, 산출물명) → ② LLM이 Action과의 관련성·판정·확신도를 판단.
- 임베딩 유사도를 ①의 보조 신호로 쓸 수 있으나 MVP에서는 키워드와 LLM으로 충분한지 먼저 본다.
- 한 발언이 여러 Action에 해당할 수 있으므로 매칭은 Action 단위로 독립 수행하고, 업무를 구분할 수 없으면 확신도 `하`다.
- **수치 임계값은 정하지 않는다.** SPEC 17장도 튜닝 대상으로 둔다. 확신도 3단계의 판단 기준(상/중/하 예시)을 프롬프트와 정답표에 명시한다.
- 보수적 기본값: 애매하면 한 단계 낮은 확신도, 즉 `확인 필요` 쪽으로 판정한다. 완료를 놓치는 비용(사람이 확인)이 완료를 잘못 올리는 비용(허위 완료 후보)보다 작다.

**잠정 결론**: 키워드 추리기 + LLM 3단계 판정. 상태 일치율 80% 목표는 정답표로 측정해 튜닝한다.

## R-05. Agent(LLM) 호출 방식

**배경**: CLAUDE.md는 `.claude/agents/`(meeting-analyst, action-manager, reviewer)와 `.claude/skills/`(analyze-meeting, check-actions)를 정의한다. 한편 Dashboard는 React + FastAPI 웹 앱이며 시연은 "업로드 → … → 승인"을 이어서 보여야 하고, 정확도 테스트는 pytest에서 자동 실행되어야 한다.

| 방식 | 장점 | 우려 |
|---|---|---|
| A. Claude Code 안에서만 실행 (skill → subagent) | CLAUDE.md 구조 그대로, 도구 권한으로 Reviewer 읽기 전용 강제 | FastAPI·pytest에서 호출하기 어려움 |
| B. Python에서 Anthropic API 직접 호출 | 앱·테스트에서 자동화 쉬움, 구조화 출력 사용 가능 | Reviewer 읽기 전용을 도구 권한이 아니라 코드 설계로 보장해야 함, `.claude/agents` 정의와 중복 |
| C. Python에서 Claude Code 헤드리스 실행 (`claude -p` 등) 또는 Agent SDK | `.claude/agents` 정의를 재사용하면서 프로그램에서 호출 | 실행 환경·지연·비용 구조 확인 필요 |

**쟁점**
- Reviewer의 "읽기 전용"은 SPEC 6.3에서 도구 권한(Read/Grep만)으로 강제하도록 정했다. B는 LLM에 도구를 주지 않고 필요한 녹취를 프롬프트로 전달하는 방식이면 사실상 읽기 전용이지만, SPEC의 표현과 달라지므로 SPEC 확인이 필요하다.
- 어떤 방식이든 LLM 출력은 `contracts/` 스키마와 코드 검증기를 거친다 (`data-model.md` 5장). 호출 방식을 바꿔도 안전장치는 유지된다.
- 구현 시점에는 최신 모델 ID와 API 사용법을 공식 문서로 확인한다.

**잠정 결론**: 미확정. 프롬프트·역할 정의는 `.claude/agents/`를 정본으로 두고, Python에서 호출 가능한 어댑터 뒤에 둔다(`plan.md` 4.3). A/B/C 중 선택은 P2 착수 전에 사용자와 정한다.

## R-06. 기한 환산 구현

**요구**: 원문 보존 + 회의일 기준 환산. 요일 단독은 회의일 이후 첫 해당 요일, 같은 요일·범위·"다음 회의까지"는 환산하지 않는다 (SPEC 5.4).

- LLM은 `due_date` **원문 추출**만 하고, `due_date_normalized`는 코드가 원문을 규칙으로 해석해 계산한다. LLM이 날짜를 계산하면 근거 없는 환산 날짜가 생길 위험이 크다 (SPEC US-03 실패 조건).
- 환산 가능한 표현은 SPEC이 이미 좁게 정했다: 요일 단독, 날짜 명시("11/12", "11월 12일"). 정규식·규칙 기반으로 충분할 가능성이 높다 (**검증 필요**: 가상 회의의 기한 표현을 모아 커버리지 확인).
- 환산 못 하는 표현은 null로 둔다 (실패가 아니라 정상 경로).
- 엣지 케이스는 정답표에 넣는다: 회의일과 같은 요일, "이번 주 금요일"(범위가 아니라 특정일로 볼지), 연도 없는 날짜의 연도(`data-model.md` 8장 #10).

**잠정 결론**: 규칙 기반 환산 모듈. 규칙에 없는 표현은 null.

## R-07. 스키마 검증 도구

- 선택지: ① `jsonschema`로 `contracts/*.json`을 직접 검증 ② pydantic 모델을 코드에 정의하고 JSON Schema를 내보내기.
- ①은 계약 파일이 곧 정본이라 중복이 없다. 이번 작업에서 `jsonschema` 4.x와 `referencing`으로 10개 스키마와 예시 29개(정상 12, 오류 17)를 검증해 동작을 확인했다.
- ②는 코드 작성이 편하지만 모델과 계약이 이중 정본이 되어 어긋날 수 있다. 쓰더라도 계약 파일과의 일치를 테스트로 묶어야 한다.

**잠정 결론**: ① `contracts/`를 정본으로 하고 경계(Agent 출력 수신, 저장, 로드)에서 `jsonschema`로 검증한다. 코드 내부에서는 dataclass 등 가벼운 타입을 쓴다.

## R-08. 원본 보호 구현 (tasks T-00-3 착수 전 확인 필요)

**문제**: SPEC 9장과 T-00-3은 `audio/**`, `transcripts/original/**`를 "신규 생성은 허용, 덮어쓰기·수정·삭제는 차단"하라고 한다. 그러나 Claude Code의 `permissions.deny`는 경로 패턴으로 도구 호출을 막는 방식이라 **"새 파일이면 허용, 기존 파일이면 차단"을 표현하지 못할 가능성이 높다** (**검증 필요**: 공식 문서로 확인). `Write` 도구를 deny하면 신규 생성도 막힌다.

**검토할 계층**

| 계층 | 막는 대상 | 한계 |
|---|---|---|
| `.claude/settings.json` deny | Claude Code의 Edit/Write 등 | 신규/기존을 구분 못 할 수 있음. Bash(`rm`, 리다이렉션, `python -c`)는 별도 규칙 필요 |
| PreToolUse Hook | Claude Code의 도구 호출 전 | 대상 파일 존재 여부를 검사해 "기존 파일이면 차단, 신규면 통과"를 구현 가능. Hook이 보는 범위(Bash 명령 파싱 등)의 한계 |
| 애플리케이션 코드 | 파이프라인이 쓰는 경로 | Claude Code 밖(Python 프로세스, FastAPI)의 쓰기는 Hook이 보지 못함. 배타적 생성(`open(path, "x")`)으로 덮어쓰기 방지 |
| 파일 속성 | 생성 직후 읽기 전용 지정 | Windows `attrib +R`/POSIX 권한. 의도적 해제는 막지 못함 |
| 해시 기록 | 변경 탐지 | 사전 차단이 아니라 사후 탐지. US-01 실패 조건("업로드 후 원본 해시 변경")과 부합 |

**잠정 결론**: 단일 수단으로는 SPEC 9장을 만족하지 못할 가능성이 크므로 **deny(Bash 포함) + PreToolUse Hook(존재 시 차단) + 애플리케이션 배타적 생성 + 생성 시 해시 기록**을 병행한다. T-00-3·T-00-4 착수 전에 deny 패턴의 실제 동작을 간단한 실험으로 확인하고, "deny만으로 신규 생성 허용"이 불가능하면 T-00-3 문구(신규 생성 허용)를 Hook 중심으로 고쳐야 하는지 SPEC 9장과 함께 정한다.

## R-09. 취소/철회 전용 상태

MVP는 철회 발언을 `확인 필요`로 처리하고 사람이 판단한다 (SPEC 5.5, 17장). 이 결정을 유지한다. 전용 상태는 tasks 14장(선택)이다. 조사할 것이 없어 보류한다.

## R-10. 벤치마크용 테스트 음성

R-01~R-03의 선택에는 정답을 아는 한국어 회의 음성이 필요하다 (SPEC 13장: 가상 회의 2개).

- **직접 녹음**: 가상 대본(정답표와 함께 작성)을 여러 사람이 읽는다. 화자 구분 평가에 가장 적합하다.
- **TTS 합성**: 화자별 다른 목소리로 합성한다. 빠르지만 실제 회의의 겹침·잡음·말 끊김과 다르다. 화자 구분 평가에는 낙관적인 결과가 나온다.
- 어느 쪽이든 실제 회사 회의는 쓰지 않는다 (CLAUDE.md).
- 정답표(`T-00-6`)에 발언별 정답 텍스트와 화자를 함께 기록해야 STT·화자 구분의 오류율을 계산할 수 있다.
- 권장: 대본 작성(T-00-5) 때 STT용 정답 텍스트를 같이 확정하고, 짧은 구간은 직접 녹음, 나머지는 TTS로 보완한다.

**측정 항목**: CER/WER, 타임스탬프 오차, 화자 오귀속 비율, `low_confidence` 재현율(오인식 구간 중 표시된 비율), 처리 시간.
