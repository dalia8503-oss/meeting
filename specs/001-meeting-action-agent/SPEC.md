# SPEC.md — Meeting Action Agent

> 개정: 2026-11-11 (요구사항·수용기준 재검토 반영). 변경 요약은 17장 참조.

## 1. 개요

**한 문장 범위**: 회의 녹음을 분석하여 지시사항을 정확하게 추출하고, 이전 회의의 지시사항 이행 여부까지 근거 기반으로 추적한다.

**컨셉**: 단순한 AI 회의록이 아니라, 회의에서 나온 지시가 실제 완료될 때까지 관리하는 Agent.

**전체 흐름**
녹음 업로드 → 녹취 → 회의 요약 → 지시사항 추출 → Reviewer 검증 → Action List → 지시사항 이행점검 → 사람 최종확인

**발표 핵심 문장**: 회의를 기록하는 AI가 아니라, 회의에서 결정된 일이 사라지지 않도록 완료될 때까지 추적하는 Agent.

## 2. 핵심 원칙

1. 녹취에 없는 내용(발언·담당자·기한·결정)을 만들지 않는다.
2. 담당자가 불명확하면 `확인 필요`로 표시한다 (화면 라벨: `담당자 확인 필요`). 추정하지 않는다.
3. 기한이 불명확하면 임의로 추정하지 않는다 (`미정` 또는 `확인 필요`, 5.4 참조).
4. 모든 지시사항에 녹취 근거와 타임스탬프를 남긴다.
5. Agent가 임의로 Action을 완료 처리하지 않는다.
6. 완료 근거 발견 시 `완료 후보`로 제안하고 사람이 최종 승인한다.
7. 원본 녹음파일과 원본 녹취록은 수정·삭제하지 않는다 (신규 생성만 허용, 9장).
8. 사람이 보강한 값은 녹취 근거가 없으므로 "사람 보강"으로 구분해 기록한다 (5.2).

## 3. 범위

### 3.1 MVP (반드시 완성)

| 구분 | 목표 |
|---|---|
| 녹음 업로드 | MP3/WAV/M4A 회의 녹음 입력 |
| 녹취 | 화자와 타임스탬프가 포함된 텍스트 생성 |
| 회의 분석 | 핵심 논의, 결정사항, 미결사항 정리 (각 항목에 근거 타임스탬프) |
| 지시 추출 | 지시자, 담당자, 업무, 기한, 근거 추출 (지시/제안 구분 포함) |
| Reviewer | 추출·이행점검 결과가 실제 녹취에 존재하는지 검증 |
| Action List | 담당자별 지시사항 목록 생성 |
| 이행점검 | 다음 회의에서 기존 지시의 이행 근거 탐색 |
| Human Check | 완료 후보를 사람이 최종 승인 |
| 안전장치 | 원본 보호, 완료 처리 보호 |

### 3.2 MVP 제외

Outlook/메일 자동 발송, Teams 자동 알림, 캘린더 자동 등록, 복잡한 권한관리, 대규모 사용자 관리, **신규 Action의 사전 사람 승인 단계**, 사람의 직접 완료 처리(완료 후보를 거치지 않는 완료), **사람의 직접 Action 생성**(빈 상태에서 사람이 새 Action을 만드는 것. Action의 최초 생성 주체는 Agent뿐이다, 5.2).

### 3.3 시간이 남으면

Dashboard 디자인 개선, SQLite 저장, MCP(SQLite Action DB ↔ MCP ↔ Claude Code), Excel 내보내기.

### 3.4 이후 확장

Outlook 메일, Teams 알림, Calendar 일정, 담당자별 Action 알림, 주간 미완료 지시 리포트, 취소/철회 전용 상태.

## 4. 사용자 스토리와 수용기준

### US-01 녹음 분석
사용자가 회의 녹음파일을 업로드하면 시스템은 녹취록을 생성한다.
- 입력 사양(초기값): MP3/WAV/M4A, 한국어, 최대 2시간. 사양 밖 입력은 오류 메시지를 내고 처리하지 않는다.
- 녹취록은 화자와 `HH:MM:SS` 타임스탬프(발언 시작 시점. 시각이 아니라 녹음 시작 기준 경과시간)를 포함한다.
- 원본 녹음파일은 변경되지 않는다.
- STT 신뢰도가 낮은 구간은 해당 발언에 `low_confidence` 표시를 남기고, 그 발언만을 근거로 한 판정은 `확인 필요`로 둔다.
- **실패 조건**: 타임스탬프 형식 오류 / 필수 필드 누락 / 업로드 후 원본 파일 해시 변경.

### US-02 지시사항 추출
회의에서 나온 지시사항을 찾아 담당자, 지시내용, 기한, 근거시간을 표시한다. 지시 여부는 5.5 분류 기준을 따른다.

예시 발언: "민수 씨, 생산성 자료 다시 확인해서 목요일 오전까지 주세요." (회의일 2026-11-10)

```text
담당자: 민수
Action: 생산성 자료 재확인
기한: 목요일 오전  (환산: 2026-11-12 오전)
근거: 00:12:31
```

- 지시가 0건인 회의는 오류가 아니다. Action 0건 + 요약만 출력한다.
- **실패 조건**: 근거 없는 Action 생성 / 제안·질문·과거 보고를 Action으로 생성 / 정답표(13장)에 있는 지시를 놓침(재현율 목표 미달, 16장).

### US-03 불명확 정보 처리
담당자 또는 기한이 확인되지 않으면 추측하지 않고 `확인 필요`로 표시한다 (기한을 명시적으로 미정이라 한 경우는 `미정`, 5.4).

예시 발언: "이거 다음번까지 확인해야겠네요."

```text
담당자: 확인 필요
기한: 확인 필요
```

- **실패 조건**: Agent가 녹취에 존재하지 않는 담당자나 기한을 생성하면 테스트 실패. 환산 날짜를 근거 없이 만든 경우도 동일.
- **실패 조건**: 녹취에 담당자가 명시돼 있는데 `확인 필요`로 둔 경우(과소추출)도 정답표 대조에서 실패로 센다.

### US-04 이행점검
다음 회의 녹음이 입력되면 기존 Action List와 비교하여 이행 여부의 근거를 찾는다.
- 결과는 `완료 후보 / 진행 중 / 미완료 / 확인 필요` 중 하나로 분류하며, 판정 기준은 5.6을 따른다.
- 각 판단에는 신규 회의의 녹취 근거(원문·화자)와 타임스탬프를 붙인다.
- 언급이 없는 Action은 `확인 필요`(근거 없음)로 둔다.
- 점검 대상은 완료가 아닌 모든 이전 Action이다. 신규 회의에서 나온 새 지시도 US-02와 같은 흐름으로 추출한다.
- **실패 조건**: 근거 없는 판정 / 타임스탬프·화자가 실제 녹취와 불일치 / Agent가 `완료`로 설정.

### US-05 사람 승인
Agent가 완료 근거를 발견해도 사람이 승인해야 최종 `완료` 상태가 된다.
- 승인 UI 선택지: `[완료] [계속 진행] [확인 필요]` (선택 후 상태는 5.6 전이표).
- 승인은 건별로 한다 (일괄 승인 없음). 승인자 이름과 승인 시각을 기록한다.
- `완료`는 `완료 후보` 상태에서만 승인할 수 있다.
- 완료 철회 후 다시 `완료`가 되려면 그 시점에 새로운 사람 승인이 필요하다. 철회 뒤에 남아 있는 이전 승인값은 승인으로 인정하지 않으며, 이전 승인과 승인자·승인 시각·근거가 모두 같은 값을 그대로 다시 쓰는 것도 유효한 새 승인으로 인정하지 않는다 (승인 이벤트는 매번 새로 발생해야 한다).
- 승인값이 없으면 `완료` 변경을 차단한다. UI뿐 아니라 저장 계층에서도 차단한다.
- **실패 조건**: 승인값 없이 `완료`가 저장됨 / 파일 직접 편집으로 `완료`가 통과됨.

### US-06 회의 요약
회의 핵심 논의, 결정사항, 미결사항을 정리한다.
- 각 항목에 근거 타임스탬프를 붙인다.
- **실패 조건**: 녹취에 없는 결정·논의가 요약에 포함됨.

## 5. 데이터 모델

### 5.1 녹취 발언 (A ↔ B 인터페이스)

```json
{
  "meeting_id": "20261110-01",
  "speaker": "팀장",
  "timestamp": "00:12:31",
  "text": "민수 씨 생산성 자료 다시 확인해서 목요일 오전까지 주세요.",
  "low_confidence": false
}
```

- `timestamp`는 발언 시작 시각이다. `low_confidence`는 선택 필드(기본 false)다.
- 필드 변경은 이 문서를 먼저 수정한다.
- B는 A의 음성 기능이 완성되기 전에도 가짜 JSON으로 병렬 개발할 수 있다.

**회의 메타데이터** (녹음 업로드 시 입력)

| 필드 | 설명 |
|---|---|
| meeting_id | 예: `20261110-01` |
| meeting_date | 회의일 `YYYY-MM-DD` (기한 환산 기준, 필수) |
| title | 회의 제목 (선택) |
| participants | 참석자 목록 (선택, 담당자 이름 대조용) |
| speaker_map | 화자 라벨 → 실명·직책 매핑 (선택). 없으면 라벨 그대로 쓰고 지시자는 `확인 필요` |

### 5.2 Action

| 필드 | 설명 |
|---|---|
| action_id | 저장소 전체에서 유일한 순번. 예: `A-001` |
| meeting_id | 발생한 회의 |
| assigner | 지시자 (불명확 시 `확인 필요`) |
| assignee | 담당자 (불명확 시 `확인 필요`) |
| task | 업무 내용 |
| due_date | 기한 **원문** (5.4). 불명확 시 `확인 필요`, 명시적 미정이면 `미정` |
| due_date_normalized | 회의일 기준 환산 `YYYY-MM-DD`. 환산 근거가 없으면 null |
| evidence | 근거 발언 원문. 여러 발언이면 `extra_evidence` 목록에 추가 |
| timestamp | 근거 타임스탬프 `HH:MM:SS` |
| status | 5.3의 상태값 |
| flags | 예: `조건부`, `지시여부애매`, `Reviewer미통과`, `기한경과`, `기한변경제안` |
| field_source | 필드별 출처: `녹취`(기본) 또는 `사람 보강`. 사람 보강 값은 근거 타임스탬프 없이 허용 |
| approved_by_human | **현재(최신) 승인 정보**: 승인자·승인 시각·근거(meeting_id, timestamp). `완료`의 필수 조건. 완료 철회 후에도 지우지 않고 보존하며, 재완료 때 새 승인으로 갱신한다 |
| history | 상태 변경과 재판정의 이력 (시각, 변경 주체 Agent/사람, 이전·이후 상태, 근거). 승인·철회 항목에는 승인 정보 스냅샷과 사람 이름을 함께 남겨, 과거 승인이 `approved_by_human`의 갱신으로 사라지지 않게 한다 |

규칙:
- 같은 회의에서 동일 담당자·업무가 반복 언급되면 하나의 Action으로 합치고 추가 발언은 `extra_evidence`에 넣는다.
- 이전 회의 Action의 재언급은 신규 Action이 아니라 이행점검 대상이다.
- 한 발언에 지시가 여럿이면 Action을 분리한다. 같은 근거 타임스탬프를 공유할 수 있다.
- 지시가 여러 발언에 걸쳐 있으면(앞 발언 업무, 뒤 발언 담당자 확정) 모든 발언을 근거로 남긴다.
- **최초 생성 주체는 Agent뿐이다 (MVP).** 사람은 Agent가 만든 후보·Action을 검토해 유지·수정·보강할 수 있으나(수정·보강 값은 `field_source: 사람 보강`), 이것이 최초 생성 주체를 사람으로 바꾸지 않는다 (history 첫 항목의 주체는 Agent). 빈 상태에서 사람이 직접 Action을 만드는 기능은 MVP에서 제외한다 (3.2).

### 5.3 상태

| 상태 | 의미 | 설정 주체 |
|---|---|---|
| 🔵 신규 | 이번 회의에서 새로 발생 (담당·기한이 확인됨 또는 기한 `미정`) | Agent |
| 🟠 진행중 | 신규 회의에서 진행 중이라는 근거가 확인됨 | Agent |
| 🟢 완료 후보 | 완료 근거를 Agent가 발견 | Agent |
| ✅ 완료 | 사람이 최종 승인 | **사람만** |
| 🔴 미완료 | 미완료 근거가 확인됨 | Agent |
| 🟡 확인 필요 | 담당/기한/완료 여부/지시 여부 불명확, 근거 없음, Reviewer 미통과 | Agent |

### 5.4 값 규칙 (담당자·기한)

**담당자**

| 상황 | assignee |
|---|---|
| 이름·직책이 발언에 명시 | 발언 표기 그대로 ("민수"). 호칭("씨", "님")만 제거 |
| 호칭만 있고 참석자 명단과 대조 시 복수 후보(동명이인) | `확인 필요` |
| 팀·부서 지칭 ("생산팀에서") | 팀 이름 그대로 허용하되 `flags`에 `팀지칭` 표시 |
| 복수 담당자 ("김대리, 박과장이") | 인원별로 Action 분리 (공동 책임은 `flags`에 `공동`) |
| 화자 자기 할당 ("제가 하겠습니다") | 화자의 실명(speaker_map). 매핑이 없으면 `확인 필요` |
| 대명사·생략 ("그거 좀 봐주세요") | `확인 필요` |
| 앞 발언 지시를 뒤 발언에서 담당자 확정 | 뒤 발언을 추가 근거로 담당자 확정 |

- 담당자가 참석자 명단에 없어도 녹취에 있으면 허용하되, 명단이 제공됐다면 `flags`에 `참석자외` 표시.

**기한**

| 상황 | due_date | due_date_normalized |
|---|---|---|
| 날짜·요일·시점이 명시 ("목요일 오전까지", "11/12") | 원문 그대로 | 회의일 기준 환산 가능 시만 값, 아니면 null |
| "다음 회의까지" | 원문 | null (다음 회의일 미확정) |
| "다음 주 초", "이번 주 내" 등 범위 표현 | 원문 | null (범위는 환산하지 않음) |
| 기한을 정하지 않기로 명시 ("기한은 나중에 정하죠") | `미정` | null |
| 해석 불가 표현 ("다음번", "조만간", "빨리") 또는 언급 없음 | `확인 필요` | null |

- 요일 단독 표현은 회의일 이후 처음 오는 해당 요일로 환산한다. 회의일과 같은 요일이면 환산하지 않는다 (null).
- 시각 표현(오전·오후)은 `due_date` 원문에만 보존한다.
- 담당자 또는 기한이 `확인 필요`이면 status는 `확인 필요`다. 기한이 `미정`인 것만으로는 `신규`다.

### 5.5 지시 분류 기준

Meeting Analyst는 발언을 아래로 분류하고, Reviewer는 이 표로 "지시가 아닌 내용을 지시로 판단"을 검증한다.

| 유형 | 예 | 처리 |
|---|---|---|
| 지시·요청 | "민수 씨, 자료 확인해서 주세요" | Action 생성 |
| 자발적 약속 | "제가 확인해 보겠습니다" | Action 생성 (assigner는 지시한 사람이 없으면 `확인 필요`) |
| 제안·의견 | "한번 확인해 보면 어떨까요" | Action 제외, 미결사항에 기록 |
| 조건부 | "견적 오면 검토합시다" | Action 생성, `flags`에 `조건부` + 조건 기재, status `확인 필요` |
| 질문·논의 | "이거 언제까지 가능할까요?" | Action 제외, 미결사항 |
| 과거 보고 | "지난주에 확인했습니다" | Action 제외 (이행점검 근거 후보) |
| 지시 여부 애매 | 위에 명확히 속하지 않음 | Action 생성, `flags`에 `지시여부애매`, status `확인 필요`. 사람이 확인 |
| 철회 | "그건 안 하기로 하죠" | 기존 Action을 `확인 필요`로 전환하고 철회 발언을 근거로 첨부 (사람이 판단) |

- 지시자는 발화자를 기본으로 하며 자격(직급) 제한은 두지 않는다. 동료 간 요청도 지시·요청이다.
- 지시·요청이 아닌 것을 Action으로 만든 경우는 Reviewer REJECT 사유다.

### 5.6 상태 전이와 이행 판정 기준

**이행 판정 (Agent, 신규 회의 녹취 기준)**

| 판정 | 조건 |
|---|---|
| 🟢 완료 후보 | 해당 Action에 매칭된 완료형 발언("했습니다", "공유했습니다", "완료")이 있고 확신도가 중간 이상. 발화자는 담당자 본인이 기본이며, 제3자 보고도 허용하되 발화자를 기록 |
| 🟠 진행중 | 진행·부분 완료 발언("작업 중", "절반 했습니다", "오늘 마무리"). 기한이 지났으면 `기한경과` 표시 |
| 🔴 미완료 | 미수행·지연을 명시한 발언("아직 못 했습니다", "미뤄졌습니다") |
| 🟡 확인 필요 | 언급 없음(기한 전·후 불문), 확신도 낮음, 근거가 `low_confidence` 구간뿐, 서로 상충하는 발언, 철회 발언 |

- **확신도**: 상/중/하 3단계. 업무 키워드·담당자·산출물명 일치와 의미 판단으로 정한다. 하이면 `확인 필요`. 수치 임계값은 튜닝 대상이다 (17장).
- 상충하는 발언이 있으면 `확인 필요`로 두고 두 근거를 모두 첨부한다.
- 한 발언이 여러 Action에 해당할 수 있다. 각 Action에 별도 판정과 근거를 붙이고, 업무를 구분할 수 없으면 확신도 하로 처리한다.
- 기한 변경 발언을 발견하면 기한을 덮어쓰지 않고 `기한변경제안`(새 기한 원문 + 근거)으로 표시한다. 반영은 사람이 한다.
- 완료 판정은 "산출물을 확인했다"는 뜻이 아니다. 산출물 확인은 사람 승인 단계의 책임이다.

**상태 전이표**

| 전이 | 주체 | 조건 |
|---|---|---|
| (없음) → 🔵 신규 / 🟡 확인 필요 | Agent | 추출 + Reviewer PASS (5.4의 status 규칙) |
| 🔵·🟠·🟡·🔴 → **현재와 다른** 🟠 / 🔴 / 🟡 / 🟢 | Agent | 이행 판정 + Reviewer PASS |
| 🟢 → ✅ 완료 | **사람** | `[완료]` 선택 + 승인자·시각 기록 (그 시점에 새로 제출한 승인) |
| 🟢 → 🟠 진행중 | 사람 | `[계속 진행]` 선택 |
| 🟢 → 🟡 확인 필요 | 사람 | `[확인 필요]` 선택 |
| ✅ → 🟠 진행중 | **사람만** | 완료 철회. 철회자 이름·시각과 철회되는 승인 정보의 스냅샷을 history에 기록 |
| 위 표에 없는 전이, Agent의 ✅ 설정 | — | 차단 |

- **자기 전이는 상태 전이가 아니다.** 진행중→진행중, 확인 필요→확인 필요처럼 상태가 그대로인 판정은 전이표의 대상이 아니며, 상태 변경 경로는 이를 거부한다. 상태는 유지하고, 새 이행점검 결과의 근거와 사유를 **재판정 기록**으로 남긴다. 재판정 기록은 history에 시간순으로 들어가며 이전·이후 상태가 같고, 근거(evidence)와 사유(note)가 필수이며 주체는 Agent다.
- **🟢 완료 후보는 사람의 최종 판단을 기다리는 상태다.** Agent는 완료 후보의 상태를 바꾸지 못한다. 완료 후보도 완료가 아니므로 이행점검 대상이며, 새 근거(완료 취소로 읽히는 발언 포함)를 발견하면 상태 변경 없이 재판정 기록으로만 남긴다. 상태 변경은 사람이 `[완료] [계속 진행] [확인 필요]`로 한다.
- **완료 철회**: 사람만 한다. 기존 `approved_by_human` 값과 과거 history는 삭제·덮어쓰기하지 않는다. 철회 후 다시 완료 후보를 거쳐 `완료`가 되면 새 승인이 `approved_by_human`을 갱신하고, 이전 승인은 history의 스냅샷으로 남는다.
- ✅ 완료 Action은 이행점검 대상에서 제외한다 (철회되어 🟠이 되면 다시 대상이다).
- 이행점검 입력의 "이전 Action List"는 사용자가 명시한다 (회의 시리즈 자동 추론은 하지 않는다).

## 6. Agent 구성

### 6.1 Meeting Analyst
- 역할: 녹취 읽기, 회의 요약, 결정사항/미결사항(각각 근거 타임스탬프 포함), 지시사항 후보 추출 (5.5 분류)
- 금지: Action 완료 처리, 원본 녹취 수정, 근거 없는 내용 생성

### 6.2 Action Manager
- 역할: Analyst 결과를 지시자·담당자·Action·기한·근거 타임스탬프·상태로 구조화(5.2~5.4). 기존 Action List와 비교해 이행 여부 분석(5.6).
- 금지: 완료 확정, 담당자·기한 추정

### 6.3 Reviewer (읽기 전용)

**검증 대상**: ① 추출된 Action ② 이행점검 판정 ③ 회의 요약의 결정사항·미결사항(근거 존재 여부).

**검증 방식**
- **코드(결정적) 검증**: 필수 필드 존재, `timestamp`가 해당 meeting의 실제 발언과 일치, `evidence`가 그 발언 `text`의 부분 문자열(공백·구두점 정규화 후), `speaker` 일치. 하나라도 어긋나면 REJECT.
- **Reviewer Agent(의미) 검증**: 담당자·기한·업무가 근거 발언과 일치하는지, 5.5 기준으로 지시인지.
- 판정은 Action 단위이며 사유를 함께 낸다. 직접 수정하지 않는다. 읽기 전용은 도구 권한(Read/Grep만)으로 강제한다.

**추출 결과 PASS**: 담당자 근거 존재 (또는 `확인 필요`가 정당 — 녹취에 담당자 후보가 없음) / Action 근거 존재 / 기한 근거 존재, `미정`, 또는 `확인 필요`가 정당 / 타임스탬프 존재

**추출 결과 REJECT**: 녹취에 없는 담당자 생성 / 녹취에 없는 기한 또는 환산 날짜 생성 / 지시가 아닌 내용을 지시로 판단 / 근거 없는 Action 생성 / 녹취에 담당자·기한이 있는데 `확인 필요`로 둠(과소추출)

**이행점검 판정 PASS**: 인용 발언이 실제로 존재(코드 검증 통과) / 그 발언이 해당 Action과 실제로 관련 / 판정이 발언 내용에서 도출됨 (예: 진행 발언을 완료 후보로 올리지 않음) / Agent가 `완료`를 설정하지 않음

**이행점검 판정 REJECT**: 위 항목 위반, 또는 근거 없이 `미완료`·`완료 후보` 판정

- 녹취에 있는 지시를 놓치는 문제(재현율)는 런타임 Reviewer 범위가 아니라 정답표 기반 테스트로 측정한다 (13·16장).

### 6.4 Multi-Agent 흐름

```text
회의 녹취 → Meeting Analyst → Action Manager → Reviewer
                                              ↙        ↘
                                          PASS        REJECT
                                           ↓             ↓
                                   Action List 저장   Action Manager 재분석 (최대 2회)
                                                          ↓ 초과
                                          사람 확인 큐 (`확인 필요` + `Reviewer미통과`)
```

- 재시도는 **최대 2회**다. REJECT 사유를 Action Manager에 전달한다.
- 2회 후에도 REJECT이면 해당 Action을 `확인 필요`, `flags`에 `Reviewer미통과`와 반려 사유를 붙여 **사람 확인 큐**(`actions/review_queue`)에 넣는다. 확정 Action List와 구분해 보이며, 사람이 유지/수정/폐기를 결정한다. 폐기도 사람만 한다. 사람의 수정·보강은 최초 생성 주체를 바꾸지 않는다 (5.2).
- 이행점검 결과도 같은 루프를 거친다.
- 신규 Action의 사전 사람 승인은 MVP에서 하지 않는다 (3.2). 사람 승인은 완료 처리 시점이다.

## 7. Skill

### `/analyze-meeting`
- 입력: 회의 녹취 + 회의 메타데이터
- 처리: 회의 요약 → 결정사항 → 지시사항(5.5 분류) → 미결사항 → 확인 필요 사항
- 출력: 구조화된 회의 분석 결과 (Reviewer 통과 전 상태로 전달)

### `/check-actions`
- 입력: 이전 Action List + 신규 회의 녹취
- 처리: 기존 Action 검색 → 이행 근거 탐색 → 상태 후보 생성 (5.6) → Reviewer 전달 (REJECT 시 재시도)
- 출력: 완료 후보 / 진행 중 / 미완료 / 확인 필요

## 8. 이행점검 시나리오

1차 회의(2026-11-10) Action:

```text
A-001 / 담당: 김대리 / 업무: 생산성 자료 수정 / 기한: 목요일 (환산 2026-11-12) / 상태: 신규
```

2차 회의 발언: "생산성 자료 수정해서 공유했습니다." (김대리, 00:08:31)

Agent 결과:

```text
A-001 완료 근거 발견 / 근거: 2차 회의 00:08:31 김대리 / 판단: 완료 후보 (확신도 상)
```

Human Check: `A-001을 완료 처리하시겠습니까? [완료] [계속 진행] [확인 필요]` — 사람이 `[완료]`를 선택하고 승인자 이름을 남겨야 최종 상태가 `완료`로 바뀐다.

## 9. 안전장치

- 보호 대상: `audio/**`, `transcripts/original/**` (deny 규칙 + Hook).
  - **신규 파일 생성은 허용**한다(업로드, 최초 원본 녹취 생성). 기존 파일의 덮어쓰기·수정·삭제는 차단한다.
- Reviewer는 읽기 전용 (도구 권한으로 강제).
- `완료` 변경 시 그 요청에 새로 제출된 `approved_by_human`을 확인하고, 없으면 저장 계층에서 차단한다. 철회 후 남아 있는 이전 승인값은 승인으로 인정하지 않는다. `actions/` 파일을 직접 편집해 `완료`로 바꾸는 경로도 검증 대상이다.
- Agent 출력의 status에 `완료`가 들어오면 거부한다.
- 저장소를 읽을 때 `history`의 모든 상태 변경(최초 생성 포함)이 5.6 전이표를 따르는지, 이력이 서로 이어지고 마지막 상태가 Action의 현재 상태와 같은지 검증한다. 재판정 기록은 상태 전이가 아니므로 이 검증과 구분하며, 상태 변경 없이 현재 상태와 일치해야 한다. 이력이 이를 어기면 오류로 처리하고 그 Action을 사용하지 않는다. 직접 파일 편집으로 전이표를 우회하는 경로를 막기 위함이다.
- 상태 변경은 모두 `history`에 남긴다. 상태가 유지되는 재판정도 같은 `history`에 시간순으로 남긴다 (5.6). 과거 승인·철회 이력은 삭제하거나 덮어쓰지 않는다.

## 10. Dashboard (웹 앱: React/Vite + FastAPI)

구성:
- **회의 요약**: 핵심 논의 / 결정사항 / 미결사항 건수
- **신규 지시**: 상태, 담당, 지시사항, 기한 (원문 + 환산). 이번 회의에서 나온 Action 전체
- **이전 지시 이행점검**: 상태, 담당, Action, 근거 타임스탬프
- **사람 확인 큐**: `Reviewer미통과`, `지시여부애매`, `조건부` Action과 사유
- 완료 후보를 선택하면 판단의 실제 녹취 근거(원문·화자·타임스탬프)를 확인할 수 있다.
- 승인 버튼(`완료` / `계속 진행` / `확인 필요`)으로 Human Check를 수행한다. 승인자 이름 입력이 필요하며 건별로만 가능하다.

예시 (2026.11.10 생산회의)

| 상태 | 담당 | 지시사항 | 기한 |
|---|---|---|---|
| 🔵 신규 | 김대리 | 생산성 자료 수정 | 목요일 (11/12) |
| 🔵 신규 | 박과장 | 업체 확인 | 미정 |

| 상태 | 담당 | Action | 근거 |
|---|---|---|---|
| 🟢 완료 후보 | 이대리 | 도면 수정 | 00:08:31 |
| 🔴 미완료 | 김대리 | 견적 확인 | 00:14:22 |
| 🟡 확인 필요 | 박대리 | 자료 작성 | 근거 없음 |

| 발표 | 회의 이해 과정 | 지시 추적 과정 | End-to-End |

공동 담당: 프로젝트 범위, SPEC.md, 수용기준, A↔B 인터페이스, Reviewer, 안전장치, 통합 테스트, Dashboard 최종 연결, 발표/시연.

## 12. 기술 스택

- 언어: Python / 테스트: pytest
- STT: **MVP는 Gemini Audio**(기존 `GEMINI_API_KEY`, 화자는 `speaker_N` 라벨만, 실명은 사람이 준 `speaker_map`으로만 적용, `low_confidence` 지표 없음 → 가짜 신뢰도 생성 금지). Whisper 계열(로컬)은 회사 실사용·보안 검토 단계의 대안으로 보류 (17장, research R-01)
- Dashboard: React 18 + TypeScript + Vite(Frontend) + FastAPI(Backend API). `MAA_MODE=live|demo`(기본 demo)는 서버 환경변수로만 정하며 요청 parameter로 바꿀 수 없다. Human Review는 `POST /api/actions/{id}/review` 단일 endpoint로 통합하고 기존 완료 가드(9장)를 그대로 거친다
- 저장: **JSON 파일**(`actions/`, `meetings/`)을 정본으로 하고 Markdown은 보고용 파생물. 여유 시 SQLite + MCP

## 13. 테스트 데이터

실제 회사 회의가 아닌 **가상의 테스트 회의 2개**와 **정답표**.

- **1차 회의**: 신규 지시사항 / 담당자 명확·불명확 / 기한 명확·불명확
- **2차 회의**: 1차 지시 완료 / 진행 중 / 미완료 / 아무 언급 없음

**반드시 포함할 케이스**

| 영역 | 케이스 |
|---|---|
| 담당자 | 명확 / 호칭만 / 팀 지칭 / 복수 / 자기 할당 / 대명사 / 앞뒤 발언으로 확정 / 녹취에 없는 이름을 유도하는 함정 |
| 기한 | 요일 / 날짜 / "다음 회의까지" / 범위 표현 / `미정` 명시 / 해석 불가 / 언급 없음 |
| 지시 유형 | 지시 / 자발적 약속 / 제안 / 조건부 / 질문 / 과거 보고 / 철회 / 애매 |
| 이행 | 완료 / 부분 완료 / 진행중 / 미완료 / 무언급 / 상충 발언 / 기한 변경 / 제3자 보고 |

**정답표**(`docs/answer_key.md` 또는 `tests/fixtures/`): Action별 담당자·기한 원문·기한 환산·지시 유형·근거 타임스탬프와, 2차 회의에서의 기대 상태·기대 근거. 모든 자동 테스트는 정답표를 기준으로 한다.

## 14. 작업 순서 (tasks.md의 기준)

1. 녹음파일 입력 → 2. 녹취 데이터 생성 → 3. Action 데이터 구조·상태 전이·완료 가드 (4와 병렬 가능) → 4. 회의 요약 → 5. 지시사항 후보 추출 → 6. Reviewer → 7. Action List 저장 → 8. 이전 Action 검색 → 9. 이행 근거 비교 → 10. 사람 승인(UI) → 11. Dashboard → 12. 통합 테스트

- 스키마(3)가 추출(5)보다 먼저 와야 추출 출력 구조가 정해진다.
- 완료 가드(저장 계층)는 3에서 구현하고, 10은 UI와 승인 기록을 맡는다.

## 15. 시연 시나리오

1. **신규 회의**: 업로드 → 녹취 → 요약 → 지시 추출 → Reviewer 검증 → Action List 생성
2. **다음 회의**: 두 번째 녹음 업로드 → 기존 Action 조회 → 이행 발언 탐색 → 완료/미완료/확인필요 분류 → Reviewer 근거 검증 → 완료 후보 제시 → 사람 최종 승인

## 16. 성공 기준

테스트 회의 2개로 다음 흐름이 처음부터 끝까지 실제 동작하면 성공.

**녹음 → 녹취 → 지시 추출 → 근거 검증 → Action 생성 → 다음 회의 분석 → 이행 근거 탐색 → 사람 승인**

**정량 기준 (정답표 대조)**

| 기준 | 목표 | 성격 |
|---|---|---|
| 녹취에 없는 담당자·기한·Action 생성 | 0건 | 필수 (위반 시 실패) |
| `완료` 상태가 사람 승인 없이 저장됨 | 0건 | 필수 |
| 제안·질문·과거 보고를 Action으로 생성 | 0건 | 필수 |
| 지시 재현율 | 90% 이상 | 초기 목표 (튜닝 대상) |
| 이행 판정 상태 일치율 | 80% 이상 | 초기 목표 (튜닝 대상) |

시연에서 보여줄 3가지:
1. Agent가 회의에 없는 지시를 만들지 않는다.
2. Reviewer가 지시사항을 원문 근거와 다시 검증한다.
3. Agent가 완료를 결정하지 않고 사람이 최종 확인한다.

## 17. 결정 사항과 미결 사항

### 확정 (2026-11-11)

| 항목 | 결정 |
|---|---|
| 기한 표기 | 원문 보존(`due_date`) + 회의일 기준 환산 별도 필드(`due_date_normalized`). `meeting_date` 필수 |
| `미정` vs `확인 필요` | `미정` = 명시적으로 미정, `확인 필요` = 언급 없음·해석 불가. Reviewer는 둘 다 PASS 가능 (정당한 경우) |
| 지시/제안 | 5.5 분류표. 제안·질문은 Action 제외, 애매하면 Action + `확인 필요` 플래그 |
| Reviewer 재시도 | 최대 2회, 초과 시 사람 확인 큐 |

### 잠정 확정 (제안, 이견 있으면 변경)

| 항목 | 결정 |
|---|---|
| 신규 Action 사전 사람 승인 | MVP 제외. 사람 승인은 완료 시점만 |
| 완료 승인 대상 | `완료 후보`에서만. 직접 완료는 MVP 제외. 승인은 건별 |
| Action 저장 형식 | JSON 정본, Markdown은 파생물 |
| 이행점검 매칭 | 키워드 + 의미 판단의 3단계 확신도, 하는 `확인 필요`. 이전 Action List는 사용자가 지정 |
| 사람 승인 인증 | 이름 입력만 (권한관리 MVP 제외) |
| 정량 목표 | 재현율 90%, 상태 일치율 80% (초기값) |
| 입력 사양 | MP3/WAV/M4A, 한국어, 최대 2시간 (초기값) |

- 취소/철회 전용 상태 신설 여부 (MVP는 `확인 필요`로 처리)
