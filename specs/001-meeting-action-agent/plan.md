# Implementation Plan — Meeting Action Agent

> 기준 문서: `SPEC.md`(요구사항·수용기준), `../../0.CLAUDE.md`(절대 원칙), `tasks.md`(작업 목록).
> 이 문서는 **어떻게 만들 것인가**만 다룬다. 요구사항을 바꾸려면 SPEC.md를 먼저 수정한다.
> 작성일: 2026-11-11 / 상태: 초안 (검토 대기)

## 1. 요약

회의 녹음 → 녹취 → 요약 → 지시 추출 → Reviewer 검증 → Action List → 이행점검 → 사람 최종 승인 흐름을 Python으로 구현한다.

핵심 설계 방침은 하나다. **"지키지 못하면 실패하는 규칙"은 LLM 프롬프트가 아니라 코드로 강제한다.**
LLM(Agent)은 추출·판단을 맡고, 근거 존재 검증·상태 전이·완료 가드·원본 보호는 결정적 코드가 맡는다.

## 2. 기술 컨텍스트

| 항목 | 내용 | 상태 |
|---|---|---|
| 언어 / 테스트 | Python, pytest | 확정 (SPEC 12장) |
| STT | Whisper 계열 | 확정. 모델·버전은 미결 |
| 화자 구분 | Whisper와 별도 처리 | **미결** (SPEC 17장) |
| Agent 실행 | Claude Code 서브에이전트(`.claude/agents/`) + Skill(`.claude/skills/`) | 확정 (0.CLAUDE.md) |
| 저장 | JSON 파일이 정본(`actions/`, `meetings/`), Markdown은 파생물 | 잠정 확정 |
| Dashboard | Streamlit 등 웹 앱 | 확정. 프레임워크는 Streamlit으로 가정 |
| 입력 사양 | MP3/WAV, 한국어, 최대 2시간 | 잠정 확정 |
| 인증 | 승인자 이름 입력만 | 잠정 확정 |
| 시간이 남으면 | SQLite, MCP, Excel 내보내기 | 선택 (tasks 14장) |

**제약**
- 원본 `audio/**`, `transcripts/original/**`는 신규 생성만 허용하고 수정·삭제는 차단한다.
- 테스트 데이터는 가상 회의만 사용한다.
- MVP 제외 항목(메일/Teams 알림, 캘린더, 권한관리, 신규 Action 사전 승인, 직접 완료 처리)은 핵심 기능 완성 전에 착수하지 않는다.

## 4. 아키텍처

### 4.1 결정적 코드와 LLM의 경계

| 영역 | 구현 방식 | 이유 |
|---|---|---|
| 녹취 스키마 검증, 타임스탬프 형식 | 코드 | 형식 오류는 실패 조건 |
| 요일 → 날짜 환산, `미정`/`확인 필요` 구분 규칙 | 코드 | 환산 오류는 허위 기한 생성에 해당 |
| 상태 전이표, 완료 가드, `history` 기록 | 코드 | 우회 불가해야 함 |
| Reviewer 코드 검증 (인용문·시각·화자 일치) | 코드 | LLM 재검증은 환각을 못 막음 |
| 회의 요약, 지시 유형 분류(5.5), 담당자·업무 추출 | LLM (Meeting Analyst) | 의미 판단 |
| 이행 발언 매칭·확신도 판정(5.6) | LLM (Action Manager) | 의미 판단 |
| 지시 여부·담당자·기한 의미 일치 검증 | LLM (Reviewer, 읽기 전용) | 의미 판단 |

**LLM 출력은 항상 스키마 검증 → 코드 검증기를 거친 뒤에만 저장한다.** 검증 실패 출력은 REJECT 루프로 보낸다.

### 4.2 데이터 흐름

```text
[신규 회의]
audio → (STT+화자구분) → transcripts/original/*.json   (신규 생성만)
      → Meeting Analyst → meetings/<id>.json (요약·결정·미결, 근거 타임스탬프)
                        → 지시 후보
      → Action Manager  → Action (5.2 스키마, status는 신규/확인 필요만)
      → Reviewer ──PASS──→ actions/<list>.json (확정 목록)
                └─REJECT→ Action Manager 재분석 (최대 2회)
                          └ 초과 → actions/review_queue (확인 필요 + Reviewer미통과)

[다음 회의]
이전 Action List(사용자 지정) + 신규 녹취
      → 점검 대상 필터(완료 제외) → 관련 발언 탐색 → 상태 후보(5.6)
      → Reviewer (같은 재시도 루프) → 이행점검 결과
      → Dashboard → 사람 [완료][계속 진행][확인 필요] → approved_by_human → 완료
```

### 4.3 모듈 구성 (제안)

> 0.CLAUDE.md의 프로젝트 구조에는 소스 디렉터리가 없다. 아래 `src/` 패키지는 **이 계획의 제안**이며, 승인되면 0.CLAUDE.md 구조도에 추가한다.

```text
src/meeting_action_agent/
├─ models/        # Transcript, MeetingMeta, Action, Status enum (SPEC 5장)
├─ rules/         # due_date 환산, assignee 표기, status 결정 (5.4)
├─ state/         # 전이표, 완료 가드 (5.6, 9장)
├─ store/         # JSON 저장·로드, review_queue, action_id 발급, history
├─ stt/           # Whisper 연동, 화자 구분, speaker_map 적용
├─ agents/        # Analyst / Action Manager / Reviewer 호출 어댑터 (LLM 경계)
├─ review/        # 코드 검증기, REJECT 루프, 큐 적재
├─ followup/      # 이전 Action 로드·필터, 이행 비교
└─ app/           # Streamlit Dashboard
```

LLM 호출은 `agents/` 인터페이스 뒤에 둔다. 단위 테스트는 고정 응답(fixture)으로, 정확도 측정(재현율·상태 일치율)은 실제 호출로 분리해 실행한다.

### 4.4 저장 계층 설계 포인트

- `action_id`는 저장소 전체에서 유일한 순번(`A-001`…)이며, 2차 회의 이후에도 이어서 발급한다.
- 상태 변경은 `store`의 단일 진입점(`change_status`)만 통과한다. 이 진입점이 전이표·완료 가드·`history` 기록을 함께 수행하며, **자기 전이는 거부**한다 (SPEC 5.6).
- 상태가 유지되는 재판정은 별도 경로(`record_reassessment`, T-03-13)가 `history`에 시간순으로 남긴다. Agent는 `완료 후보`의 상태를 바꾸지 못하고 재판정만 기록하며, `완료` Action에 대한 재판정 요청은 거부한다.
- `완료` 전이는 그 요청에 새로 제출된 승인으로만 가능하다. 완료 철회(사람만) 후에도 `approved_by_human`과 과거 `history`(승인 스냅샷 포함)는 삭제·덮어쓰지 않으며, 남은 승인값으로 재완료할 수 없다.
- 파일을 읽어 올 때 `history`의 모든 상태 변경(최초 생성 포함)이 전이표를 따르고 이어지는지, 마지막 상태가 현재 `status`와 같은지 검증한다(재판정 항목은 구분, T-03-14). 또한 `완료` 상태의 `approved_by_human`·`history` 정합성(사람의 `완료 후보`→`완료` 전이와 승인 스냅샷 일치)과, `kind` 없는 자기 전이 이력을 검증해 오류로 처리한다. 직접 편집 우회를 막는다.
- Action의 최초 생성 주체는 Agent뿐이다 (history 첫 항목의 주체).
- Markdown 보고서는 JSON에서 생성만 하고 되읽지 않는다.

- P0의 **정답표(T-00-6)** 가 모든 정확성 테스트의 기준이므로 가장 먼저 확정한다.
- P1~P3 완료 시점에 "가짜 녹취 → Action 저장"이 처음으로 끝까지 동작해야 한다.

## 6. 마일스톤과 검증

| 마일스톤 | 통과 조건 |
|---|---|

| M2 1차 회의 분석 | 정답표 기준 허위 담당자·기한·Action 0건, US-02·US-03 예시 통과 |
| M3 Reviewer | 변조한 타임스탬프·인용문·가짜 담당자가 REJECT, 재시도 2회 초과 시 큐 적재 |

**정량 기준 (SPEC 16장)**: 필수 3건(허위 생성 0, 무승인 `완료` 0, 제안·질문 Action 0)은 위반 시 실패. 재현율 90%, 상태 일치율 80%는 초기 목표이며 튜닝 대상이다.

**테스트 구성**
- 단위: 전이표, 완료 가드, 값 규칙, 코드 검증기 (LLM 불필요, 항상 실행)
- 정답표 기반: Analyst/Action Manager 출력 대조 (LLM 응답 fixture 또는 실제 호출)
- 수용기준 매핑: US-01~US-06 실패 조건을 `docs/acceptance_map.md`로 관리, 단위 테스트 재사용 (T-12-3)
- 안전장치: 원본 덮어쓰기·삭제, 직접 파일 편집으로 `완료` 변경 시도
